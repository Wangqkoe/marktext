# 完整的 Codex 协作开发流程

本指南描述一种可长期复用的协作开发方式：让用户负责产品决策，让协调任务控制范围和质量，让执行任务在小而清晰的边界内交付可验证的改动。

> **核心原则：** 实现任务说“完成”，只表示该任务的改动和证据已交回；它不等于改动已经集成、经过独立审查，或已经通过最终验收。

## 一行总流程

规则与基线 → 探索与原型确认 → Spec → Tickets → 独立实现与提交 → 分层 Review → 集成与自动验收 → 人工试用与缺陷循环 → 最终 Review/Acceptance → 发布、归档与清理。

## 1. 先建立规则、职责与可恢复的基线

在仓库根目录维护 `AGENTS.md`，作为所有任务的共同约束。它至少应说明：

- 是否允许推送、提交、发布或修改外部服务；默认只做用户授权的动作。
- 分支、提交信息、格式化、测试和构建的项目约定。
- 协调任务、执行任务和用户各自的决策边界；执行任务不得擅自扩大需求。
- 哪些变更属于高风险（例如持久化、并发、跨模块疑难、严重故障修复），以及相应的模型和独立复审要求。
- 工作区已有的用户修改必须保留。开始前记录 `git status`；不要把无关的已跟踪或未跟踪文件纳入本次提交。

建立基线时，协调任务应产出一份简短记录，包含当前分支与提交、`git status`、可运行的测试/类型检查/lint/构建命令、关键目录和入口点。必要时补充代码地图：模块职责、调用边界、状态/数据流、关键测试与构建入口。代码地图是后续拆票和影响分析的依据，应随集成持续更新。

并行读取、搜索、分析和运行只读检查通常安全；并行写代码则必须避免同一文件、同一接口或同一行为的冲突。为每张写入票分配独立任务和 worktree，并在拆票时声明文件所有权与依赖关系。

## 2. 探索需求并先确认体验

不要把一句需求直接当成实现说明。协调任务先与用户确认问题、目标用户、成功信号、边界条件和非目标；查看现有实现、类似功能、日志或可复现步骤。若视觉或交互是依据，保存可追溯的产品证据：参考截图、录屏、状态说明、尺寸/平台信息及允许推断的范围。

对 UI、布局、交互状态或复杂流程，优先制作低成本原型：线框图、静态页面、交互演示或最小可运行样例。用原型确认信息层级、状态转换、错误路径和平台行为，再进入正式实现。用户确认应明确记录“确认了什么”和“尚未确认什么”；没有确认的关键体验不要假设为已定稿。

## 3. 将确认结果写成正式 Spec

每个可开发阶段都应有可评审的 Spec，而不是仅有聊天记录。建议包含：

| 项目 | 需要写清的内容 |
| --- | --- |
| 目标 | 要解决的问题、用户收益和可观察的成功结果 |
| 范围 | 本阶段会改变的页面、模块、平台和数据 |
| 非范围 | 明确不做的需求、延后事项和兼容性边界 |
| 行为 | 正常流程、状态、错误处理、权限、边界输入和回退方式 |
| 产品证据 | 已确认的原型、截图、现有行为或决策记录 |
| 验收标准 | 可测试、可观察、可判定的条件及所需环境 |
| 风险与未知项 | 需验证的假设、技术风险、依赖和负责人 |

Spec 在开始实现前由用户或被授权的产品决策者确认。变更 Spec 时，更新版本/日期和受影响 Tickets；不要让实现悄悄偏离已确认范围。

## 4. 从 Spec 拆出可验收 Tickets

每张 Ticket 只交付一个可独立检查的结果，并写明：输入 Spec、目标和非目标、涉及模块/文件、前置依赖、风险等级、验收命令或人工检查、回归范围，以及提交边界。依赖先后要显式标注，形成实现 frontier（当前已集成能力、待做边界和阻塞项）。

推荐按风险选择执行配置：

- 常规代码、测试、文档和构建产物：`gpt-5.6-terra`、`medium`。
- 数据丢失或持久化、并发、跨模块疑难、严重问题修复及关键最终复审：`gpt-5.6-terra`、`high`。
- 验收标准明确的机械性状态、地图、清单或固定命令：可使用 `gpt-5.6-luna`、`medium`。

协调任务负责拆分、排序、决策、冲突消解和最终核验；执行任务直接完成已界定 Ticket，不递归派发子任务。每张 Ticket 使用独立任务/worktree，防止并行改动互相覆盖。

## 5. Ticket 的标准实现循环

执行任务按以下检查点工作，并把证据随结果交回：

1. **读取约束：** 阅读 `AGENTS.md`、Spec、Ticket、相关代码地图和当前工作区状态；确认不触碰已有用户修改。
2. **复现或建立测试：** 能复现则记录准确步骤；不能复现则建立最小测试、夹具或观察证据，并说明限制。
3. **最小修改：** 只修改完成 Ticket 所必需的代码、测试和文档；不顺带重构无关区域。
4. **验证：** 运行与改动风险相称的单元、集成/E2E、类型检查、lint、构建或人工验证。
5. **Diff 检查：** 审阅 `git diff` 与 `git status`，确认没有生成物、密钥、格式噪声或用户已有改动被纳入。
6. **本地提交：** 只提交该 Ticket 的文件，使用清楚的本地 commit；除非另获授权，绝不推送。
7. **返回证据：** 返回提交 SHA、变更摘要、运行命令及结果、未运行项目和已知限制。

## 6. 分层 Review 与集成

执行者自检关注“我是否按 Ticket 做完且没有明显回归”。它不能替代独立 Review。独立 Review 至少分两轴进行：

| 层次 | 要回答的问题 |
| --- | --- |
| Standards Review | 是否符合仓库规则、架构边界、代码质量、测试约定与安全要求？ |
| Spec Review | 是否精确满足已确认的目标、范围、行为和验收标准？ |

高风险改动、跨模块改动、持久化、并发、严重修复和最终关卡必须由未实现该改动的独立任务审查。发现问题应创建或回流到 Ticket，附上影响、复现和优先级；不要用“看起来没问题”代替记录。

协调任务在通过必要 Review 后集成提交，处理冲突并再次检查集成后的差异。每次集成更新代码地图和 frontier：已完成/已验证的边界、下一批可并行 Tickets、仍被阻塞的依赖以及已知风险。

## 7. 阶段性自动验收

每次集成和每个阶段结束时，运行适用的自动验收。至少评估单元测试、集成/E2E、类型检查、lint、构建和 `git status`。结果表必须显式使用以下状态之一：

| 状态 | 含义 |
| --- | --- |
| Passed | 已运行且通过 |
| Failed | 已运行但失败，附失败摘要和处理决定 |
| Skipped | 已知适用但本阶段有明确理由未运行 |
| Unavailable | 环境、凭据、平台或工具不可用 |
| Untested | 尚未执行或不具备足够验证；不能被当作通过 |

验收报告还应写明命令、环境、覆盖范围和限制。`git status` 应显示只有预期改动；用户原有修改仍应保留且与本次提交隔离。

## 8. 人工试用版与平台验证

自动测试通过后，构建一个可由人试用的版本，并按产品实际平台验证。桌面/原生应用至少考虑：OS 原生交互、剪贴板、文件打开/保存对话框、字体回退与缩放、高 DPI/多显示器、安装与首次启动、升级/卸载（若本阶段涉及）。

记录测试 OS、版本、缩放比例、安装包/构建标识、实际步骤、预期与实际结果。人工试用用于发现自动化难覆盖的体验问题，不应被简化为“打开过一次”。

## 9. 长期 Bug 修复循环

缺陷不是一次性清单，而是持续闭环：收集 → 去重 → 分级 → 复现 → Ticket → 修复 → 独立复审 → 回归验证。每条缺陷应保留影响范围、环境、复现步骤、日志/截图、严重度、关联版本与状态。

- 严重问题（数据损坏、崩溃、安全、关键路径不可用）阻塞后续发布，并优先获得独立审查和回归验证。
- 中低优先级问题可以进入已知问题或后续 backlog，但必须记录原因、影响和计划入口，不能在验收中悄然忽略。

修复要补上能防止复发的测试或明确说明为何不能自动化；回归范围除了原复现步骤，还包括受影响模块、平台和相邻关键路径。

## 10. 最终 Review 不等于最终 Acceptance

最终 Review 是工程质量关：独立核对代码、架构、风险、测试证据、差异和已知问题，判断是否符合 Standards 与 Spec。最终 Acceptance 是产品交付关：用户或其授权代表在目标环境确认可用性、体验和业务目标。

两者都通过才可宣布该阶段完成。若 Review 通过但用户试用发现需求不符，回到 Spec/Ticket；若用户喜欢效果但 Review 发现严重风险，仍必须先修复或获得明确的风险接受决定。

## 11. 交付、归档与清理

发布前形成版本记录：版本号/提交 SHA、变更摘要、兼容性或迁移说明、验证矩阵、已知问题及规避方式。构建产物应能关联到源提交和构建环境。

阶段完成后归档已关闭任务、Review 结论和验收证据；保留未完成缺陷的负责人和入口。确认本地提交已被需要的集成分支包含后，清理不再使用的 worktree 与临时分支。清理前再次确认目标路径和未提交修改，绝不删除用户工作或仍有价值的证据。

## 三方职责表

| 角色 | 主要职责 | 不应替代 |
| --- | --- | --- |
| 用户 | 定义优先级、确认目标/原型/Spec、接受或拒绝风险、进行最终 Acceptance | 不必替实现者逐行验证代码 |
| 协调任务 | 建立基线、澄清范围、拆票排期、分配 worktree、监控依赖、组织 Review、集成与验收 | 不应让“任务完成”自动变成“项目已验收” |
| 执行任务 | 在 Ticket 边界内实现、测试、自检、本地提交并返回可复核证据 | 不应改变产品范围、吞并用户修改或自行宣布最终交付 |

## 阶段完成判定清单

- [ ] Spec、范围与验收标准已确认，非范围已记录。
- [ ] 所有已纳入 Tickets 均有本地提交、实现证据和依赖状态。
- [ ] 必要的独立 Standards Review 与 Spec Review 已通过或遗留项已获明确处理。
- [ ] 自动验收结果已按 Passed/Failed/Skipped/Unavailable/Untested 记录。
- [ ] 适用的人工试用和平台验证已完成。
- [ ] 严重缺陷为零；其余已知问题已分级、记录并有后续入口。
- [ ] 集成提交、代码地图/frontier、版本记录和任务归档已更新。
- [ ] `git status` 已检查，用户已有修改被保留且没有被误提交。
- [ ] 最终 Review 与用户/授权代表的最终 Acceptance 均已完成。

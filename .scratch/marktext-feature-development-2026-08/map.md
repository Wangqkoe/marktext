# MarkText 新一轮功能开发探索地图

Label: `wayfinder:map`
Status: `exploring`

## Destination

建立一条可恢复、可审查、可逐项推进的 MarkText 新功能开发路线：先记录用户提出的真实需求和产品证据，识别它们之间的依赖与风险，在必要时用低成本原型确认体验，再将已确认的范围转化为 Spec、可验收 Tickets、实现、独立 Review 和最终 Acceptance。

本地图当前只承载探索框架。用户尚未提出具体功能，因此不预设功能、优先级、技术方案或交付日期。

## 本轮规则 / 基线

- 遵守仓库 [AGENTS.md](../../AGENTS.md)、[CONTEXT.md](../../CONTEXT.md) 和 [docs/codex-development-workflow.md](../../docs/codex-development-workflow.md)；所有变更只提交本地仓库，不推送 GitHub。
- 本会话由协调任务负责需求探索、范围决策、拆票、依赖监控、集成和验收；具体代码、测试、文档和构建实现由独立执行任务完成。执行任务不得自行扩大范围或递归拆任务。
- 用户负责确认目标、优先级、关键体验、Spec 和产品风险接受；未确认的关键体验不得视为已定稿。
- 开始每个阶段前记录可恢复基线：分支、提交、`git status`、可运行的检查命令、相关模块和既有用户修改。既有修改必须保留并与本轮改动隔离。
- 本轮创建时基线为：branch `codex/latex-math-delimiters-v0.20.0`，HEAD `db2de1cba774eb00cd8257163ad40cf6e33fd88a`；开始时唯一既有工作区改动是未跟踪的 `CONTEXT.md`。该文件必须保留，并排除在后续本轮提交之外。
- 已知根级验证命令为 `pnpm test:unit`、`pnpm test:e2e`、`pnpm typecheck`、`pnpm lint`、`pnpm build:unpack`；具体需求出现后仅按适用性执行，并记录 Passed/Failed/Skipped/Unavailable/Untested 及限制。
- 先理解问题和成功信号，再决定是否实现；现有行为、类似功能、日志、复现步骤、截图和原型均是证据，不能把参考产品自动当成规范。
- 每张 Ticket 应有单一可检查结果、明确文件/模块边界、前置依赖、风险等级、验收命令或人工步骤、回归范围和提交边界。
- 实现任务“完成”只表示该 Ticket 已交回证据，不代表已集成、独立 Review 通过或最终 Acceptance 通过。
- 高风险改动（数据丢失/持久化、并发、跨模块疑难、严重问题修复、关键最终复审）必须升级为独立高强度 Review；相关执行/审查任务使用 `gpt-5.6-terra`、`high`。常规代码、测试、文档和构建实现使用 `gpt-5.6-terra`、`medium`；验收标准明确的机械地图、清单或固定命令任务可使用 `gpt-5.6-luna`、`medium`。实现和审查均保持本地。

## 需求记录模板

每项用户需求单独登记为 `R-##`，在用户确认前保持 `exploring`，不得填入臆测的实现细节。

| 字段 | 记录内容 |
| --- | --- |
| ID / 标题 | `R-##`；一句可检索的需求标题 |
| 来源与日期 | 用户原话、提出日期、关联对话或证据路径 |
| 问题 / 目标用户 | 谁在什么场景遇到什么问题；期望收益是什么 |
| 成功信号 | 可观察、可测量或可人工判定的结果 |
| 目标平台 / 环境 | Windows、macOS、Linux、缩放、主题、文档规模等；未知写明未知 |
| 范围 | 本阶段明确会改变的行为、界面、模块、数据或平台 |
| 非范围 / 延后项 | 明确不改变的行为、兼容边界和后续方向 |
| 现状与证据 | 当前实现位置、类似行为、复现步骤、日志、截图、现有测试；无证据须标注 |
| 未知与待决策 | 需要用户或技术验证的假设，逐项指定决策人和截止关卡 |
| 依赖 | 前置需求/能力、共享接口、数据迁移、平台或外部工具依赖，引用 `R-##`/`T-##` |
| 依赖类型 | `hard`、`soft`、`shared-seam`、`validation-only`（见下文） |
| 风险等级 | `low`、`medium`、`high`，附影响、概率和缓解方式 |
| 原型关卡 | 是否需要原型；关卡目标、输入、输出、确认人和通过条件 |
| Spec / Tickets | 关联 Spec 版本、Ticket 编号及实现 frontier 状态 |
| 验收 | 自动检查、人工试用、平台矩阵、回归范围和证据位置 |
| 状态 / 下一步 | 使用本地图的状态流；写明唯一下一动作和阻塞原因 |

## 依赖类型与 frontier 规则

- `hard`：没有前置结果就无法安全定义或实现；前置项未通过时，后续保持 `blocked`，不得绕过依赖假设实现。
- `soft`：可并行探索但会影响方案、优先级或体验；先记录假设，若前置结论变化则回到受影响的探索关卡。
- `shared-seam`：多个需求依赖同一状态、接口、持久化、编辑器或 IPC 边界；先做共享契约/原型决策，再拆相互独立的实现 Tickets，避免并行改同一 seam。
- `validation-only`：实现可先行，但需目标平台、数据样本、用户确认或外部工具才能验收；在证据缺失时状态只能是 `validation-pending`，不能报告 Passed。

Frontier 每次推进都要显式更新，至少包含：

- `done/accepted`：已确认范围、已集成提交、已完成独立 Review 和验收证据；仅此部分可作为后续工作的稳定基线。
- `ready`：所有 `hard` 依赖已满足、范围和验收标准已确认，可拆或执行。
- `exploring`：仍在收集需求、现状证据或产品决策，不能创建实现 Ticket。
- `blocked`：被明确依赖、环境或用户决策阻塞，记录阻塞责任与解除条件。
- `validation-pending`：实现/Review 可能完成，但缺目标平台、人工试用或其他验收证据。

每次完成一个节点后，只开放其直接下游；若共享 seam、持久化或并发状态发生变化，重新评估所有下游依赖并安排独立 Review。

## 风险分级与升级规则

| 等级 | 典型影响 | 要求 |
| --- | --- | --- |
| `low` | 局部文案、孤立样式、无状态的低影响交互 | 最小实现、相关测试或人工检查、常规 Standards/Spec Review |
| `medium` | 跨组件行为、编辑器交互、平台差异、性能或兼容性变化 | 明确回归矩阵、受影响模块检查、独立 Review；必要时先原型 |
| `high` | 数据丢失/损坏、持久化/迁移、并发/竞态、跨模块疑难、崩溃/安全、核心路径不可用、关键最终复审 | 停止扩大 frontier；建立可复现证据和回退方案；使用高强度独立 Review，运行相称的全量/高风险测试，并由协调任务和用户/授权决策者处理风险接受 |

以下任一情况立即从 `low/medium` 升级 `high`：可能丢失或静默改写用户文档/设置；涉及文件同步、恢复、序列化、IPC、共享编辑器状态或竞态；跨平台行为无法由现有测试覆盖；出现崩溃、安全问题或核心工作流阻塞；独立 Review 发现未解决的严重问题；回归范围无法界定或无法安全回滚。

## 原型验证判定与原型关卡

当需求包含新布局/视觉层级、复杂交互或状态转换、错误/回退路径、平台原生行为、不可逆操作，或存在两个以上合理方案且代码实现成本较高时，默认先做低成本原型。纯机械、已有明确行为契约且无体验不确定性的改动可跳过原型，但须记录理由。

原型只回答被选定的问题，不替代正式实现。每个原型关卡记录：

1. `P-##` 目标：待验证的体验假设和不验证的内容。
2. 受控范围：线框、静态页面、交互演示或最小样例；禁止顺带改产品代码。
3. 关键状态：正常、空状态、加载、错误、取消、恢复/回退和边界尺寸（适用时）。
4. 评估证据：截图/录屏、步骤、平台/尺寸/缩放、可观察结果和已知限制。
5. 通过条件：由用户确认的选择、成功信号和未决问题；未确认不得进入 Spec。

## 状态流

`idea` → `exploring` → （不需原型：`user-confirmed`；需原型：`prototype-needed` → `prototype-review` → `user-confirmed`）→ `spec-draft` → `spec-accepted` → `ticket-ready` → `implementing` → `implemented-local` → `standards-review` + `spec-review` → `integrated` → `acceptance-pending` → `accepted` → `archived`

是否需要原型必须依据“原型验证判定与原型关卡”记录并由协调任务明确标注；不需原型的需求不得被迫经过原型关卡，需原型的需求则不能绕过原型评审直接进入 `spec-draft`。

旁路状态：

- 依赖未满足：任意前置状态 → `blocked` → 依赖解除后返回原状态。
- 需求或原型被否决：→ `deferred` 或 `rejected`，保留原因，不创建实现 Ticket。
- 验收证据缺失：实现/Review 后 → `validation-pending`，补齐证据后再进入 `integrated`/`accepted`。
- 发现范围偏离或严重缺陷：回退到 `exploring`/`spec-draft`/对应 Ticket，禁止以“已实现”掩盖未决问题。
